# 让前端再死一次：个人开发者怎么做出自己真正满意的页面

> 标题是标题党，先说结论：前端不会死，死的是「为了 4px 的间距，跟 AI 来回描述二十分钟」这种沟通成本。

## 一、AI 写的页面，总是差一口气

这两个月我几乎所有的页面都是让 agent 先写的。说实话，第一版通常能到 80 分：结构对、文案像样、配色不出错。

但剩下那 20 分，才是决定一个页面「能不能拿出去见人」的地方。

- 卡片圆角太硬，从 12px 调到 16px 就顺眼了；
- 标题和副标题之间空得太开，行高从 1.6 压到 1.45；
- 按钮悬停只想让它轻轻浮起 2px，而不是放大 1.04 倍；
- 那一排里多了一个重复的「立即体验」按钮，其实应该删掉；
- 购物车点「加入」之后会闪一下「已加入 ✓」，半秒后又弹回去 —— 这个状态到底怎么定？

这些事情有一个共同点：**它们都是「看到才知道」的决定，不是「想到就能说清」的需求。**

## 二、为什么「跟 AI 说」效率这么低

我试过认真描述：「这几张卡片之间再松一点，但不要那种很空的松，是呼吸感的松」。

Agent 很听话，给我加了 `gap: 32px`。我看了一眼，不对，是 24px。再改，还是不对，可能是内边距的问题。

来回五轮，二十分钟过去了。二十分钟里我做的事，本质上就是**用语言去传输一个视觉判断**。

语言的带宽太低了。一个滑块拖动 0.3 秒就能表达「再大一点」，翻译成文字要几十个字，还要赌对方理解得对不对。

这就是我想做的东西的起点：**让人用人的方式改，让 AI 用 AI 的方式改，两边改同一个文件。**

## 三、把「编辑器」做成 agent 的工具

我做了一个叫 **page-tuner** 的小工具：一个本地 MCP 服务 + 一个只绑 `127.0.0.1` 的可视化编辑器。

流程只有四步：

1. Agent 把页面写出来，调 `html_editor` 起编辑器，把 URL 甩给我；
2. 我在网页里点选、拖滑块、调悬停、删掉多余元素、点「一键排版」；
3. 我圈住那块「还是不对」的区域，选一个意图（改样式 / 改文案 / 加元素 / 整块交给你），写一句人话；
4. Agent 先读我这一路的改动日志，再审我的圈选意图，改完文件，编辑器 1 秒内自动同步回来。

关键在**第 4 步的「先读日志」**。

以前 agent 改完页面，我再手动改一遍，它下次进来完全不知道我动过什么。我删掉的重复按钮，它会在下一轮「优化」里热心地加回来 —— 因为它只看到「页面上少了个按钮」，看不到「这是人有意删的」。

所以编辑器把人的每个动作都记成结构化的一条：

```json
{"type":"delete","id":"e31","tag":"button","cls":"cta","text":"立即体验"}
{"type":"text","from":"立即购买","to":"立即下单"}
{"type":"move","dx":-12,"dy":0}
```

Agent 一个 `html_changes` 调用就能读完，知道谁被删了、谁挪了、文案从什么改成了什么。**它不再猜，也不会把我删掉的东西加回来。**

## 四、三个让它「真的能用」的技术点

市面上不缺 AI 页面生成器，缺的是「人改完还能交回给 AI」的闭环。为了这个闭环，踩了三个坑：

### 1. 源码级手术，不是重新生成

Agent 生成整页 HTML 很快，但「重新生成」意味着人之前所有微调全部作废。

`page-tuner` 用标签索引做局部替换：只重写受影响的那一段，没碰到的字节一个都不动。你改一个圆角，文件的其余 99% 保持原样，diff 干净得像手写的。

### 2. 两层样式，才写得出 `:hover`

内联样式优先级最高，而且**表达不了 `:hover`**。如果所有样式都写 inline，「悬停时上浮」这个需求永远做不出来。

所以工具把样式拆成两层：

- 几何类（字号、行高、内边距、宽度、位移）走 inline，改一次定型；
- 视觉类（颜色、背景、渐变、透明度、阴影、圆角、transform）写进唯一类名 `.pt-N` 的 `<style>` 块。

写状态规则前，先把 inline 里的同名基础值搬进 base 规则再摘掉 inline，选择器用 `.pt-N.pt-N:hover` 提高权重。这套绕法不优雅，但它是「人在浏览器里改完，agent 还能继续改」的前提。

### 3. 稳定的 id 和「改动日志」

两边要协作，得先有共同语言。`data-ct-id="eN"` 按 DOM 顺序编号，编辑器和 MCP 用同一套；人选中的是 `e26`，agent 收到的也是 `e26`。

再加上前面说的改动日志侧车（`<page>.changes.json`）和选区侧车（`<page>.selection.json`），人和 AI 之间就有了可审计的「交接单」。

## 五、它不解决什么

我不想把它吹成万能：

- 只支持单文件静态 HTML。带构建工具的前端工程不在范围内；
- 不支持自由拖到任意坐标 —— 文档流里乱拖会把后面的块拖塌，这是浏览器的事实，不是偷懒；
- 写死在页面 JS 里的瞬时状态（比如「已加入 ✓」半秒回弹），CSS 改不到，还是要人圈出来、agent 去改事件处理和 `setTimeout`；
- 它没有替你做设计。审美还是你的，工具只是把「想到」到「看到」之间的距离缩短到 1 秒。

## 六、谁适合用

- 独立开发者：一个人既要写逻辑又要调视觉，最缺的就是这种「不用描述、直接上手」的反馈速度；
- 小团队里没有专职前端的项目：产品经理自己拖两下，比写十条需求文档快；
- 用 Claude / Cursor / Trae 写页面的任何人：你已经有一个会写代码的 agent 了，缺的是一个能让人插手、又能把结果交回去的中间层。
